Execution layer addendum v0.1 (2026-05-14) DRAFT

Not signed off. Companion to v1.0 (which is the alignment-ready outline). Closes the post-approval execution gap surfaced in the May 14 Conductor squad standup.

Six new pages under the EXEC section nav prefix. All content drawn from the Conductor Task Execution Layer addendum (v0.1), which extends v1.0 with the trigger model, executor registry, execution result schema, state machine wiring, worked examples, and open questions for the execution layer.

  • New page execution-overview.html — Overview of the execution layer, why it exists, what v1.0 owns vs what this addendum owns, core definitions (trigger, action, executor, execution contract, execution attempt, reconciler sweep), the 5-element execution contract, agent layer boundary, and 5 reference patterns borrowed from external tools (Notion automations, GitHub Actions, Zapier, Temporal, Airflow).
  • New page execution-triggers.html — Trigger model. Four trigger types (immediate, scheduled, on-event, manual-fire), each with backing implementation. v1 on-event trigger registry (6 events mapped to v1.0 streams with latency targets). Engineering call for event bus tech choice (Postgres LISTEN/NOTIFY recommendation for v1).
  • New page execution-executors.html — Action-to-executor binding via the executor registry (8-column versioned table). Five v1 executor types (message_send, message_compose, hotel_search, pre_arrival_template, human_routing) with input/output contracts, failure modes, and latency targets. Coverage check against v1.0 Appendix F (all 15 v1 task subtypes resolve to at least one executor). Phased rollout (v1/v2/v3).
  • New page execution-state.html — Execution result schema (separate task_execution table with 11 columns), state machine diagram (approval to trigger resolution to executor start to terminal states), status transitions (9 execution events mapped to canonical status transitions), retry policy (none in v1, fail loudly), reconciler sweep (24-hour scan for orphans), edge cases and failure modes (11 cases).
  • New page execution-examples.html — Four worked execution examples mirroring v1.0 Appendix D structure. Each example shows the resolved execution contract (5 elements) and execution attempt rows (success path, plus failure path for the Aman Tokyo hotel search). Examples: Aman Tokyo hotel search, Seoul typhoon disruption, pre-arrival checklist, scheduled anniversary message (the Sunthar 00:15:50 use case from the standup).
  • New page execution-questions.html — 12 alignment-meeting questions for the execution layer. Covers execution result storage (separate table vs denormalised), retry policy per task_type, event bus tech, executor registry storage progression, pause-resume model for long-running tasks, cancellation cascading, how failures route to humans, sub-task spawn pattern, trigger event payload schemas, min acceptable result threshold, operator-facing executor visibility, composite executor failure-mode visibility.
  • Draft banner Every new page shows an amber-bordered draft banner at the top: "Execution layer addendum · v0.1 draft proposal — Not signed off. Companion to v1.0 (which is the alignment-ready outline). Read v1.0 first; this addendum closes the post-approval execution gap."

v1.0 schema hardening (2026-05-13)

Post-v1.0 schema gap audit applied in-place to v1.0 (no version bump). Adds enumerations and new fields to close out the data model before engineering writes specs.

  • status enum status field enumerated: pending / in_progress / blocked / snoozed / done / dismissed. Reopen of a closed task transitions back to in_progress (with reopen_count + last_reopened_at updated); reopen does not get its own status.
  • priority enum priority enumerated: High / Normal / Low, default Normal. Auto-bump rules deferred to §8 q13.
  • filter rename (§7.2) Stale source filter renamed creation_surface to match the actual schema field. source wasn't a real field.
  • +6 fields (§7.2) Six new schema fields: snooze_until (pairs with snoozed status), dismissal_reason (audit-required when status → dismissed), reopen_count + last_reopened_at (close out §8 q10 audit + recovery), parent_task_id + agent_run_id (link agent-mode sub-tasks back to the agent run). Schema grows 23 → 29 fields.
  • activity log (§7.2) Activity log specified as a separate entity: per-task append-only log capturing every state transition with timestamp / actor / event type / before-after values. Engineering: separate table with FK to task; not denormalised onto the canonical record.
  • conf. threshold (§7.1 Stage 3) Confidence threshold storage specified: per-(origin × task_type) tunable config table; default 0.90 across the matrix, calibrated downward over time as operator-acceptance signals accumulate.
  • agent linkage (§7.1 agent mode) Schema linkage specified: AI sub-tasks carry both parent_task_id and agent_run_id; human sub-tasks carry agent_run_id only.
  • App. D update (Example records) Six new fields added to D.1 / D.2 / D.3 worked records (all empty / default — none of the three example scenarios exercise snooze / dismissal / reopen / agent-mode).

v1.0 (2026-05-13) — applying call feedback from the v0.2 PM review

  • Exec Executive summary added at top of doc. Narrative form (Amazon-style), about one page, covers problem statement, 4-stage flow, five origin buckets, routing tiers, task-type-driven rendering, open questions, and what-this-doc-is-not. Designed to make the alignment review decidable in 2 minutes if the reader doesn't want to dig deeper.
  • v1/v2 gate (§7.1 Stage 3) Approval gate phased evolution rewritten. v1 (launch): every suggestion goes through human review; confidence_score captured from day 1 for telemetry / calibration only. v2 (post-calibration): auto-approve above a threshold (e.g. ~90%) per task type.   • +4 fields (§7.2) Four new canonical task fields: action (verb-phrase), actor (who or what executes), when (execution timing), and confidence_score (AI certainty 0-1, drives v1 telemetry + v2 auto-approval gating). Schema grows 19 → 23 fields. Appendix D worked records updated with the new fields populated.
  • task_type (§7.2) task_family renamed to task_type and elevated from "to be defined in the PRD" placeholder to a load-bearing concept. Type drives (a) where the task surfaces in the UI and (b) which fields are visible per surface.
  • Appendix F (new) Task types and rollout phases. Nine task_type categories phased into v1 / v2 / v3: v1 covers messaging, booking-action, trip-prep, and disruption-response; v2 covers member-context, ops-internal, and agent-subtask; v3 covers compliance-safety and discovery.   • AI replies (§7.1) AI-suggested replies are tasks — explicit callout added. AI-proposed message replies travel the same 4-stage flow with one-click inline approval; canonical task created and auto-closed in the same step. Audit trail (who approved sending which message) preserved in one canonical record.
  • §8 trim (18 → 15) Merged three pairs of overlapping questions: VVIP bypass + VVIP detection (was q9 + q17) became one VVIP policy question; closure-confidence model + per-origin closure mapping (was q5 + q13) became one closure model question; soft-closed audit state + reopen loop (was q10 + q14) became one closure audit + recovery question.

Did not pre-lock — added as new §8 open question 11. §7.2 intro updated from "single dashboard" to "task board" to match.

Chose to keep Signal and Suggestion as separate concepts (not collapsed per the PM's "signal / suggestion" framing) because the distinction earns its keep when multiple signals correlate into one suggestion or signals get filtered out as non-task-worthy. Stage-by-stage description includes the rationale + evidence surfacing at the approval-gate stage (per C10 Explainability).

New Appendix E adds three worked walkthroughs: PR-review for a Client-driven booking request, Incident for a World-driven typhoon alert, and Incident with multi-signal correlation (3 inputs → 1 task) — which demonstrates the correlation property that motivated keeping Signal and Suggestion as separate concepts in Piece 1.
